关键约束：

- **单向为主**：数据只能从源 → ETL → 库 → API → 页面；唯一反向链路是管理台触发采集。
- **采集与查询解耦**：API 只读库，Never 直接调数据源；采集失败不影响看板可用（读到的是上次成功的数据 + `asOf` 日期）。
- **前端不做二次计算**：金额统一「亿元」，聚合在 ETL 里算好，页面只渲染。

## 2. ETL 采集流水线

```mermaid
flowchart LR
    START(["python etl.py<br/>incremental / all / meta / members / moneyflow / aggregate"]) --> CFG{"读 token / 连库"}
    CFG -->|"无 token"| EX2["退出码 2"]
    CFG -->|"连库失败"| EX1["退出码 1"]
    CFG -->|"成功"| AUD["audit_start<br/>t_fetch_log(status=running)"]
    AUD --> META["meta<br/>trade_cal + index_classify(SW2021)"]
    META --> BASIC["stock_basic 全量"]
    BASIC --> MEM["index_member × 511<br/>（L1 源端无数据 → 恒为 0 行）"]
    MEM --> MF["moneyflow<br/>主窗口 + 空洞自愈（下界=库内最早交易日，单轮≤50 天）"]
    MF --> DAY{"逐日：分页拉取（页大小 6000）"}
    DAY -->|"has_more 未消化 / 单日异常"| PROB["记 problem + failed_days<br/>（继续跑，不中断）"]
    DAY -->|"正常"| AGG["aggregate L2 → L3 → L1<br/>只重算本次写入的日期"]
    AGG --> FIN["audit_finish<br/>status=success / partial"]
    PROB --> FIN
    FIN --> CODE{"problems 为空？"}
    CODE -->|"是"| OK(["退出码 0"])
    CODE -->|"否"| THREE(["退出码 3"])
```

设计要点（每条都有对应事故或审查项）：

| 机制 | 为什么必须有 |
|---|---|
| 分页按「实回行数」推进 offset | 服务端硬顶 6000 行/页，`t_stock_basic` 已达 93% 容量，不翻页就静默截断 |
| 幂等 upsert | 任何一天都能单独重跑，`incremental` 可反复执行 |
| 空洞自愈 | 断点/漏采的交易日无需人工 SQL，下一轮自动回填 |
| 逐日 try/except + `failed_days` | 单日失败不能拖垮整轮，但**必须体现在退出码**（0 以外的 3） |
| 审计行 `t_fetch_log` | API 靠它判断「是否已有采集在跑」（跨进程护栏） |
| 聚合只算写入日期 | 242 天全量重聚合要 44 s，增量应接近 0 |

## 3. 一次 API 请求的生命周期

```mermaid
sequenceDiagram
    autonumber
    participant B as 浏览器
    participant MW as 中间件<br/>traceId + ACCESS
    participant R as router
    participant S as service<br/>60s TTL 缓存
    participant POOL as 连接池(8)
    participant DB as MySQL

    B->>MW: GET /api/v1/industries?level=2&page_size=20
    MW->>MW: 生成 traceId（ContextVar）
    MW->>R: 转发
    R->>S: list_industries(...)
    alt 缓存命中（< 60s）
        S-->>R: 直接返回（3 ms 级）
    else 未命中
        S->>POOL: acquire()（ping 失败自动重连）
        POOL->>DB: 参数化只读 SQL（SQL 侧下推 5d/10d 求和 + top-4）
        DB-->>POOL: 结果集
        POOL-->>S: release()（rollback 归还）
        S-->>R: Envelope（camelCase 响应模型）
    end
    R-->>MW: {code:0,msg:"ok",data}
    MW-->>B: HTTP 200 + X-Trace-Id
    Note over MW,B: 一切错误也是 HTTP 200 + code≠0：<br/>40001 参数 / 40102 密钥 / 40301 IP<br/>40401 对象不存在 / 42901 采集中<br/>42902 限流 / 50000 兜底
```

## 4. 管理台触发采集（唯一的反向链路）

```mermaid
sequenceDiagram
    autonumber
    participant U as 管理台 admin.html
    participant A as /api/v1/admin/fetch
    participant G as FetchGate + t_fetch_log
    participant W as 子进程 python etl.py
    participant DB as MySQL

    U->>A: POST /admin/fetch（X-Admin-Key）
    A->>G: admin_guard（fail-closed）<br/>IP 白名单 → 限流 30 次/分 → 常量时间比 key
    alt 校验失败
        G-->>U: 40301 / 42902 / 40102
    else 已有 running 行（360 分钟内）
        G-->>U: 42901 采集进行中
    else 通过
        G->>G: 抢占 FetchGate（原子，抢不到即 42901）
        G->>W: spawn，stdout 重定向 etl_run.log
        G-->>U: {code:0,data:{task,status:"accepted"}}
    end
    loop 前端每 ~2s 轮询
        U->>A: GET /admin/log?lines=N&offset=M
        A-->>U: {lines,total,mtime}
    end
    W->>DB: upsert 业务表 + 写审计行
    U->>U: 日志出现「退出码 0」→ 刷新看板
```

要点：

- **两层防重**：进程内 `FetchGate`（原子占锁，worker 结束才释放）+ 数据库 `t_fetch_log` 的 running 行（跨进程、跨重启有效；超过 `FETCH_STALE_MINUTES=360` 视为崩溃残留）。
- **ETL 是子进程**：`etl.py` 改完立即生效，**不需要重启 uvicorn**；`app/**` 改完才需要重启。
- 采集期间 API 只读路径不受影响（不同连接）。

## 5. 数据表关系

```mermaid
erDiagram
    t_industry ||--o{ t_industry_member : "sw_code（含 in_date/out_date 时点有效）"
    t_stock_basic ||--o{ t_industry_member : "ts_code"
    t_stock_basic ||--o{ t_moneyflow : "ts_code"
    t_trade_cal ||--o{ t_moneyflow : "trade_date"
    t_industry ||--o{ t_industry_flow : "sw_code + level"
    t_trade_cal ||--o{ t_industry_flow : "trade_date"
    t_industry ||--o{ t_industry : "parent_code（三级树）"
```

三处容易踩的口径：

1. `t_industry_member` 用 `in_date / out_date` 做**时点成分**：聚合某日资金流必须按 `in_date <= trade_date < out_date` 关联，不能直接 join「当前成分」。
2. `t_industry_flow` 是**物化聚合结果**（`level` 1/2/3），源数据变了要重算，不能直接读 `t_moneyflow` 现场算。
3. `t_industry_member` 里 **L1 恒为 0 行**：一级行业由二级聚合而来（`parent_code`），这是设计，不是漏采。

## 6. 采集任务状态机（`t_fetch_log.status`）

```mermaid
stateDiagram-v2
    [*] --> running: audit_start 插入一行 running
    running --> success: 无 problem → 退出码 0
    running --> partial: 有失败日 / 分页截断 / 成分股失败 → 退出码 3
    running --> stale: 进程崩溃或被强杀（没走到 audit_finish）
    stale --> idle: 距 start_at 超过 FETCH_STALE_MINUTES（360 分钟）
    success --> [*]
    partial --> [*]
    idle --> [*]
```

`partial` 是**部分成功**，不是失败：已写入的交易日有效，重跑 `incremental` 会自动补齐未完成的日期。
