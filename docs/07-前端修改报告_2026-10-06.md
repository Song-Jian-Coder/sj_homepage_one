### 2.4 ✅ 搜索请求风暴（报告 6.3 P0）—— 实测从 300+ 降到 0

这条我做了**三层处理**，因为实测发现报告只描述了其中一层：

**第一层：默认展开从「全部节点」收窄为「仅命中节点」**（报告描述的那层）

原 `autoOpen = (q || hits) ? '1' : '0'` 全局生效，导致每个三级节点的 `data-open`
都是 `'1'`。现改为按节点判定：`l3Hit()` / `l2Open` / `l1Open` / `gapOpen` 各自判断。

**第二层：空闲态必须全部收起**（报告**没有**描述，我实测发现的）

我第一版把逻辑写成 `(!searchOn || l3Hit(...))`，语义正好反了 —— 空闲态变成全展开。
实测首屏立刻对 **300+ 个三级节点**同时发 `/members`：

```
GET /api/v1/industries/850151/members?x=1&page=1&page_size=100
GET /api/v1/industries/850152/members?x=1&page=1&page_size=100
... （共 300+ 条，实测抓包）
```

修正为 `(!narrowing || ...)` 后：

| | 首屏(空闲) | 搜索「0」后 |
|---|---|---|
| 修改后 | **0 个请求** | 267 个（仅命中节点，合理） |
| 最大并发 | — | **6**（限流生效） |

**第三层（我额外加的）：并发闸门**

即便只开命中节点，宽泛查询（如一个「0」命中 309 个行业）仍会有 267 个请求。
报告 §9.3-8 要求「只对命中节点 auto-open，并串行/限流请求」——
我实现了一个 6 并发的信号量 `_fillPump()`，替换原来裸的
`querySelectorAll(...).forEach(fillStocks)`：

- 展开大一级行业、点「全部展开」、启动时深链跳转，**三个入口统一走队列**；
- 队列在 `renderTree()` 时重置，避免上一轮失效 DOM 的节点堆积；
- 节点已脱离文档（`!node.isConnected`）时直接丢弃。

实测 `maxInflight = 6`，与设计一致。

### 2.5 ✅ 树重建 O(n²)（报告 6.3 P0）

`loadTree()` 里建立三个索引，把 `findL3` / `findL2Of` 从三层嵌套线性扫描

## 4. P1 项：可维护性与一致性

### 4.1 ✅ 两套 API 调用层合一，并处理 422（报告 6.4 / 6.5）

`industry.html` 原本同时有 `_api()`（容忍缺 `code` 字段）与 `apiGet()`
（`code !== 0` 就抛错），且**两者都不认 FastAPI 的 `422 {"detail":[...]}`** ——
于是报告说的「文档承诺的 422 形态在前端退化成一句无信息的『数据接口错误』」。

合一为 `common.js` 的 `api()`：

- 统一处理三种形态：`{code,msg}`（业务错误）、HTTP 4xx/5xx、`{detail:[...]}`（422 校验）；
- 422 的 `detail` 会被压成一行可读文案（`q: String should have at least 1 character`）；
- `ApiError` 携带 `code` / `traceId`，满足报告 A4「客户端凭 traceId 对账」的意图。

> 口径同报告 §10：凡我无法按建议实施、或我自己的判断被实测推翻的，都写在这里。

### 7.1 偏离：报告建议的 CSP `script-src 'self'` **不可直接实施**

报告 §9.3-1 第 4 步建议加 CSP `script-src 'self'` 作为兜底防线。
**实测这条会导致三个页面全部白屏**：

```
LOG[error]: Executing inline script violates the following Content Security Policy
directive 'script-src 'self''. Either the 'unsafe-inline' keyword, a hash
('sha256-suPJTIh5VjhixMlWSWEUiafWYCbnRyS88Nq7YhOW2aI='), or a nonce ... is required
页面状态: treeLen=0, l1count=0, statLine=""   ← 白屏
```

原因：这三个页面**全部业务逻辑就是一个大内联 `<script>` 块**
（单文件、无构建步骤）。`'self'` 会把它自己拦掉。

**我的取舍**：保留 CSP，但 `script-src` 显式带 `'unsafe-inline'`，
只保留**确实能加固、且不自伤**的指令：

```
object-src 'none'     封掉 object/embed 插件类注入
base-uri 'self'       封掉 base 标签劫持（改写相对 URL 的经典手法）
form-action 'self'    封掉表单外发（防凭据外泄）
default-src 'self' + 各资源域白名单   封掉第三方资源加载
```

**为什么不走 hash/nonce**：hash 方案下每次编辑页面都会使 hash 失效 → 页面静默白屏；
对一个「无构建步骤、靠人手改 HTML」的项目，这个代价高于收益，而且会制造
报告反复强调的那类「静默失败」。**真正严格的 `script-src` 应由反向代理层用
nonce 下发 HTTP 头实现**（`docs/01` 的 P3 计划已提到 Nginx）——
这一点我写进了页内注释，需要后端/运维配合。

### 7.2 我自己引入的回归 #1：`apiGet is not defined`

把 `apiGet` 从 `industry.html` 移到 `common.js` 时，我只挂了 `SW.apiGet`，
忘了挂全局。实测：

```
ReferenceError: apiGet is not defined
  at http://127.0.0.1:8000/industry.html:2211:3
treeHead: "<div class="empty">数据加载失败：apiGet is not defined<br><br>..."
```

页面没白屏，但**静默变成了错误空态** —— 正是报告批评的那种失败模式。
修正：把所有页面直接调用的名字（`esc`/`escAttr`/`yi`/`fmtAmt`/`fmtYi`/`cls`/
`tsCode`/`bareCode`/`api`/`apiGet`/`fnum`…）都挂到全局。

**并加了一条护栏**：写了个静态检查脚本，把所有页面的「裸函数调用」
与 `common.js` 实际导出的名字做差集，提前发现「少挂一个全局」。
它随后又抓出了第二、第三个同类问题（`fmtYi`、`escAttr`），说明这条护栏有价值。

### 7.3 我自己引入的回归 #2：`exName is not defined`

我把 `exName` 和 `esc`/`yi`/`cls` 一起当「重复的工具函数」删了，
但**它其实只有一份定义、且仍被调用**（`openStock` 里显示「上交所/深交所」）。
修正：把 `exName` 保留在页面内。

### 7.4 我自己引入的回归 #3：交易所筛选变成「无匹配」（已修，并因此多修好 2 项既有失败）

我把 `autoOpen` 逻辑反转后，点击「上交所」时整棵树变成 0 个节点：

```
点击「上交所」后: l1=0, l2=0, l3=0, statLine="无匹配"
```

根因是一个**报告没有描述的语义歧义**：`matchCount()` 在「仅交易所筛选」
（无关键词、但 `exFilter != 'all'`）时也返回非 `null` 的 `hits`，
但它的各个集合**全是空的** —— 收窄其实是由 `exCount()` 里的按 `ex` 过滤完成的。
`countL3` 的第 3 步（未缓存时只有 `l2hit` 才展示）于是把所有节点判成 0。

原实现没暴露这个问题，是因为 `autoOpen='1'` 强制展开并填充了缓存，
把 bug 掩盖住了 —— **这正好是报告 §9.3-9 想修的那个「靠展开掩盖问题」的模式。**

修正：新增 `isPureExFilter(hits)` 显式识别这种状态，
`countL3` / `gapCount` / `hasGap` 三处口径统一，`renderTree` 用 `narrowing`
（而非 `searchOn`）决定是否收窄。统计行也从「无匹配」改为显示筛选提示。

**副作用是好的**：报告记录的 22/24 里那 2 项失败
（「筛选上交所只留 SH」「筛选深交所只留 SZ」）**因此被修好**，回归达到 24/24。
