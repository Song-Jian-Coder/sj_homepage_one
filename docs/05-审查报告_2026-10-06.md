## 3. 审查结论的正确性声明（先讲我改判了什么）

为了避免让读者被夸大或失真的结论误导，这里先列出**复核后我下调或纠正的 3 条**：

### 3.1 「`_seriesCache` 未声明导致运行时 `ReferenceError`」→ 实为**死代码**，不是线上故障

子代理报告：diff 删掉了 `const _seriesCache = new Map();`，但 `industry.html` 仍在调用它。

- **前半句成立**：`HEAD:552` 有声明，当前工作区 `backend/static/industry.html` 中
  `_seriesCache` **只剩 2 处引用（L1857、L1864）而没有任何声明**。
- **但影响面被高估**：`genSeries` 全文件**只有定义（L1855）、没有任何调用点**；
  经全文件检索，`genSeries`/`amountBaseOf`（L1879）都只有 1 处出现（即定义本身）。
  所以那段代码永远不会执行，`ReferenceError` 是**潜伏的**，不会导致页面白屏。
- **正确定性**：**死代码 + 潜伏错误**（Medium），不是 Blocker。顺带说明：本仓库该处
  也没有任何测试能发现它 —— 这本身才是真问题。

### 3.2 「成员表唯一键导致重复活跃成员、聚合金额翻倍」→ 是**表结构隐患**，当前数据是干净的

子代理报告：`uk_member(index_code, con_code, in_date)` 含 `in_date`，源端修正 `in_date`
时会插入新行而旧行（`out_date IS NULL`）残留 → 同一只股票算两次。

- **机制成立**（`schema.sql:44` 确实含 `in_date`；`etl.py:186-190` 是 ODKU）。
- **但我实测核对了现网数据**：
  `SELECT ... FROM t_industry_member WHERE out_date IS NULL GROUP BY index_code, con_code HAVING COUNT(*)>1`
  → **0 条**。当前没有重复活跃成员，聚合金额**没有**翻倍。
- **正确定性**：**潜伏的表结构缺陷**（Medium），修复成本低（唯一键去掉 `in_date`），
  但不该按「已经在错」来描述。

### 3.3 「ETL 日志里的行数」→ 确认**被放大 2 倍**，这条复核后成立

子代理指出 `db.execute` 返回的是 ODKU 的 `rowcount`（更新计 2、未变计 0），日志因此误导。
复核：`etl_run.log` 记「L1 聚合 **15066** 行」，而 `t_industry_flow` 中 `level=1` 实际
**7533** 行 —— 正好 2 倍。**成立**，详见 5.4。

### 3.4 「`/industries/{非二级}/flow` 返回空序列」→ **不成立**，是文档错误带偏了结论

前端子代理依据 `docs/03:259`「仅二级行业有数据」，报告 `industry.html:1024,1087`
在 L1/L3 节点上挂资金流按钮会导致「面板静默空白」（C-D，High）。

**连库实测反驳了这个结论**：

| 层级 | 抽样代码 | `t_industry_flow` 行数 |
|---|---|---|
| L1 电子 | `801080` | **243 行**（2025-09-29 ~ 2026-09-30） |
| L2 半导体 | `801081` | 243 行 |
| L3 林业Ⅲ | `850131` | **0 行** |

- **L1 完全正常**（31 个一级行业每个都有 243 天数据）→ 「非二级返回空」不成立。
- **L3 是另一回事**：`850131` 这类三级行业之所以没数据，是因为**它在数据源端就没有成分股**
  （`docs/04:46` 自己写明「346 个三级行业里 72 个在源端为空」）。
  所以前端遇到的是**真实的数据稀疏**，不是后端按层级过滤掉了数据。

**正确定性**：`docs/03:259/316` 这两句话是**错的**（见 5.7.4），
它把一个「数据源稀疏」问题误导成了「后端不支持三级」。真正的缺陷在前端
—— 对确实没有数据的 L3 节点缺少「暂无成分股」的空态（该空态函数
`showNoMember` 存在但不可达，见 6.4）—— 而不是后端接口分层。

> 这正好说明了两轴分离的价值：**依赖错误文档得出的「代码 bug」结论，
> 会在错误的方向上花掉工程师的时间。**

各处对「根目录 `industry.html` 与 `backend/static/industry.html` 差多少」说法不一

优先级标记：**P0**=上线前必修　**P1**=近期修　**P2**=排期修

### 5.1 正确性

#### 5.1.1 【P0】`/health` 的降级分支不可达，且 DB 一挂就 500

`main.py:83-92`

```python
@app.get("/api/v1/health")
def health(conn=Depends(get_conn)):
    try:
        db.query_one(conn, "SELECT 1")
        db_up = "up"
    except Exception:
        db_up = "down"                                  # ← 永远不会走到
    r = db.query_one(conn, "SELECT MAX(trade_date) FROM t_industry_flow")   # ← 在 try 之外
```

两个独立缺陷：

1. `get_conn`（`main.py:54-60`）在**进入函数体之前**就执行了 `db.connect()`。
   MySQL 不可达时依赖注入阶段就抛异常，`health` 根本不会被调用 → 直接 500。
   所以那个 `try/except` 恰好捕获不了它真正想捕获的失败。
2. 即使连接成功，L90 的 `SELECT MAX(...)` 在 `try` **之外**，查询失败同样 500。

结果：`docs/01 §8` 承诺的「健康检查返回 DB 连通性」，在 DB 真的挂掉时**从来说不出 `down`**。

**修**：把连接获取+两条查询都纳入同一 `try`，失败时返回
`{"status":"down","db":"down","latestTradeDate":None}` 且仍用 HTTP 200 业务码。

#### 5.1.2 【P0】`/admin/fetch` 的并发护栏是空操作

`main.py:495,507-514`

```python
_fetching = threading.Lock()
...
if not _fetching.acquire(blocking=False):
    return err(42901, "fetch already running")
try:
    threading.Thread(target=etl.main, args=([task],), daemon=True).start()
    return ok({"task": task, "status": "accepted"})
finally:
    _fetching.release()          # ← 线程刚启动就释放，锁形同虚设
```

`finally` 紧跟 `start()` 执行，所以锁只覆盖「创建线程」这一瞬。
并发 POST 两次 → 两个 ETL 同时跑，且 `etl.py:44` 的 `Logger` 以 `"w"` 打开**同一份**
`etl_run.log`，两者会互相截断。`docs/03 §1.2/§3.12` 承诺的 `42901` 实际不可达。

另注：这是进程内全局锁，多 worker 部署下同样无效。

**修**：把状态交给 worker 持有 —— 模块级 `threading.Event()`，
worker 进入时 `set()`、`finally` 里 `clear()`；入口只检查 `is_set()`。
多进程场景需改用文件锁或 DB 标志位。

etl.py:77   rows, _ = client.call("trade_cal", ...)        ← has_more 被丢弃

#### 5.1.4 【P1】聚合日志的行数被放大 2 倍（已实测确认）

`db.py:12-15` 的 `execute()` 返回 pymysql 的 `rowcount`；在 `ON DUPLICATE KEY UPDATE` 下
语义是「插入计 1、更新计 2、未变计 0」。证据：`etl_run.log` 记「L1 聚合 **15066** 行」，
而库里 `level=1` 实际 **7533** 行 —— 正好 2 倍。`sync_trade_cal` 的「写入 0 行」同理误导。

因 `t_fetch_log` 从未写入（见 5.6），日志是**唯一**的采集审计来源，所以这个数字不能不准。

**修**：区分 inserted/updated（如对比执行前后 `COUNT(*)`），或直接记
`affected_rows` 并明确标注语义。

#### 5.1.5 【P1】`float()` 兜底不一致，NULL 会打成 500

同一份「净流入序列」,三个地方三种写法：

| 位置 | 写法 |
|---|---|
| `main.py:345-353`（行业 flow） | ✅ 逐个 `float(x) if x is not None else None` |
| `main.py:392-395`（个股 flow） | ❌ `float(x["sm"])` 裸调用 —— `NULL` → `TypeError` → 500 |
| `main.py:193`（`_win_sum`） | ⚠️ `float(d[t].get(key) or 0)` —— **把 NULL 当 0**，静默失真 |

`main.py:260-261` 的 `sum(x["net"] for x in fl[:5])` 同样无 NULL 兜底。
**修**：统一一个 `fnum(v)` / `sumnull()` 工具函数，三处调用同一个。

#### 5.1.6 【P1】`norm_date` 不做校验，非法日期直达 MySQL

`main.py:70-74` 只做 `s.replace("-","")`。`?start=abc` 会带着 `'abc'` 去比较 `DATE` 列，
MySQL 报 1292 → 未捕获 → 500，并通过 5.2.1 把内部错误原文回显给客户端。

**修**：用 `datetime.strptime` 或正则校验，失败返回 `err(40001, ...)`。

#### 5.1.7 【P2】空洞扫描窗口 = 主窗口，早于窗口的空洞永不发现

`etl.py:343-345` 取 `win_min = min(all_days)`，而 `all_days` 受
`MONEYFLOW_DAYS`（默认 40）限制（`etl.py:270-272`）。所以扫描范围恰好等于主窗口，
更早的历史空洞永远不会被回填 —— 日志里的「空洞扫描：242 个交易日全齐」
正说明窗口本身就是那 242 天，而非真实全量。`etl.py:256-258` 的 docstring
「不再受回溯窗口限制」与实现不符。

**修**：扫描下界改用 `SELECT MIN(trade_date) FROM t_moneyflow`，或把文档改成「窗口=主窗口」。

#### 5.1.8 【P1】单日采集失败不影响退出码与响应

`etl.py:312-317,329-332`：逐日失败只写日志，`sync_moneyflow` 照常返回，
`main()` 返回 0。而 `/admin/fetch` 早已回了 `accepted`。调用方**无法知道「有 N 天没采到」**。

**修**：把失败日数上抛为退出码；配合 5.6 写审计表。

#### 5.1.9 【P2】时区不统一

`etl.py:74-76` 用 `date.today()`（进程本地时区），`etl.py:271` 用 `CURDATE()`（MySQL 会话时区），
而 `trade_date` 的语义是 Asia/Shanghai。若主机跑 UTC，盘后运行会把当日交易日判为未来日而空转一天。

**修**：进程与 MySQL 会话统一 `+08:00`，并在启动日志里打印生效时区。

#### 5.1.10 【P2】404 语义在同资源上不统一

`main.py:250-252`、`331-333`、`366-367` 对不存在的代码返回 `40401`；
但 `main.py:313`（`/members`）和 `main.py:452`（`/stocks-flow`）对不存在的行业返回
`code:0` + 空列表。前端无法区分「行业不存在」和「行业存在但暂无成分股」。

#### 5.1.11 【P2】残留的旧错误提示文案

`backend/static/industry.html:1820` 的兜底提示仍写着
「请确认 `data/stocks.json` 与本文件在同一目录下」，
但现行页面**已不再读 `data/stocks.json`**（改从 API 构建）。该文件现仅被旧版
`申万行业分类浏览.html:488` 使用。属误导性死文案。

### 5.2 安全性

#### 5.2.1 【P0】未捕获异常把内部细节回给客户端

`main.py:77-79`

```python
@app.exception_handler(Exception)
async def unhandled(request: Request, exc: Exception):
    return JSONResponse(status_code=500, content=err(50000, str(exc)))
```

`str(exc)` 会把 pymysql 原文回显，例如
`(1045, "Access denied for user 'root'@'localhost' (using password: YES)")`，
以及表名、含 SQL 片段的异常、文件路径。直接违反 `docs/01 §6.7`「日志脱敏 / 响应脱敏」。

**修**：响应体固定为 `"internal error"` + `traceId`；细节只写服务端日志，凭 `traceId` 对账。

#### 5.2.2 【P1】管理密钥用非常量时间比较

`main.py:503,522`：`if x_admin_key != ADMIN_KEY:` 是短路字符串比较。
配合 5.2.1 的差异化响应，理论上可做计时侧信道。

**修**：`hmac.compare_digest(x_admin_key, ADMIN_KEY)`。

#### 5.2.3 【P1】上游是明文 HTTP，token 走请求体

`config.py:33` 默认 `http://221.204.19.233:7172`；`tushare_client.py:82-89` 把

**修**：改用官方 HTTPS、或给代理套隧道/HTTPS 网关；`TS_ENDPOINT` 为 `http://` 时启动打警告；
token 文件（`config.py:8` 指向 `C:\Users\57424\jsdata_tk.csv`）加文件 ACL。

1. 把 `industry.html:724` 的 `esc` 抽成共享函数（例如 `backend/static/common.js`）；
2. 在三个页面的**所有**插值处调用它 —— 不要只加 `<`/`>` 替换而漏掉 `"`；
3. 优先给动态字符串插值改写成 `textContent`（结构性解法，不需要记得转义）；
4. 加一条 CSP（`script-src 'self'`）作为兜底防线。

`admin.html:431-432` 的日志渲染已经做了 `&<>` 转义，可对照参考。

#### 6.2.2 【P1】管理台页面本身无任何访问控制

`backend/static/admin.html` 是静态文件，任何能访问服务的人都能打开它、看到控制台外壳
（API 仍受密钥保护）。配合 6.2.1 的 XSS 与 5.2.5 的 `CORS *`，风险叠加。

#### 6.2.3 【P2】`ADMIN_KEY` 存 `localStorage`

`admin.html:232-233` 自己也提示了「请勿在公共设备上保存」。
`localStorage` 对同源脚本完全可读，所以任何一处 XSS 都会升级为密钥失窃。
**修**：改为仅存 `sessionStorage`，或干脆不持久化（每次手输）。

#### 6.2.4 【P2】无第三方脚本，但有未加 SRI 的 Google Fonts

实测：7 个页面中 `<script src="http(s)://...">` 命中 **0**，`XMLHttpRequest` 命中 **0**，
`eval`/`new Function`/`document.write` 命中 **0**，**无任何硬编码的凭据/token/管理密钥** —— 这些都是好的。

但每个页面头部都引用了 Google Fonts CSS（`<link href="https://fonts.googleapis.com/...">`，
各页 `:7-9` 附近），**没有 `integrity`、没有 `crossorigin`**。
两点影响：① 第三方 CSS 无完整性校验；② 客户内网演示环境若无外网，
字体解析失败会影响排版观感。建议自托管字体或直接去掉。

### 6.3 性能

- **【P0】一次搜索会触发「请求风暴」。** `industry.html:1012`
  `autoOpen = (q||hits) ? '1' : '0'` 会把**每一个**三级节点的 `data-open` 都置为 1，
  随后 `:1113` 的 `fillOpenL3()` 为**每个**节点各发一次 `/members` 请求
  （单节点还可能翻多页）。一次宽泛查询 = 几十到上百个并发请求，
  彻底击穿 `:819-821` 的懒加载设计。**修**：只对命中节点 `auto-open`，并串行/限流请求。

- **【P0】每敲一个键就重建整棵树两次，且带 O(n²) 扫描。**
  `industry.html:1094` 每次重建全部 **511** 个节点，而且**每次渲染跑两遍**
  （`:1747-1748` 一次、`:816` 再一次）；`countL3:849` 内又调用
  `findL3:949` 与 `findL2Of:938`，二者各自对约 480 个节点做线性扫描
  → 单次渲染约 **33 万次**访问。**修**：在 `loadTree()` 里建 `code → node` 的 `Map` 索引，
  并给搜索输入加防抖（目前搜索输入本身有防抖，但树重建路径没有）。

- **【P1】两次多余的重量级请求。** `industry.html:597` 为了拿计数请求
  `/industries?level=2|3&page_size=1000`，但 `main.py:234` 证明 `/tree` **已经返回
  `memberCount` 和 `directMemberCount`** —— 两个各带上文 5–6 条查询、含
  10 日窗口聚合的全量列表请求被白白浪费。**修**：直接用 `/tree` 的字段。

- **【P1】`_rankCache` 从未写入，且「全市场强度排名」在比较不同窗口。**
  `industry.html:1325` 的 `_rankCache` 没有任何写入口；`:1293` 的自身强度是**窗口内**口径，
  而 `/strength`（`main.py:490`）是**全历史累计**口径 → 两者不可比，
  排名结果没有意义。**修**：统一口径（见 5.7.10）。

- **【P1】全量历史重复下载。** `genSeries:1860`、`genQuad:1887`、行业资金流 `:1919`
  都**不带 `start`/`end`**，把全部 242 个点拉回来再在前端 `slice`；
  而缓存键是 `code|days` → 切换周期会把同一份负载重新下载一遍。
  **修**：把窗口下推到 `start`/`end`（后端已支持），缓存键按 `code|start|end`。

- **【P1】`data/stocks.json` 126 KB 被复制两份**：`data/stocks.json` 与
  `backend/static/data/stocks.json` 字节相同，且仍被公开托管在 `/data/stocks.json`。

- **【P1】`fundflow.html` 有 25% 是死数组。** `:387` 内嵌了 **11,233 字符**

- **【P2】大表整体重建**：`fundflow.html:489`、`admin.html:626` 每次都用

## 7. 双轴对照（Standards / Spec）

### 10.1 ✅ 其 §4.1 反证**成立**：本报告 5.7.2 的影响面是错的（已撤回）

**结论：我错了。** 我原来的论断是「不带 `q` 请求 `/stocks/search` 会执行 `LIKE '%%'` 返回全部 5,571 只股票」。
**实测返回 HTTP 422 `string_too_short`，端点根本不执行。**

我做了两个实验，互相印证：

1. **机制隔离实验**（最小 FastAPI 应用，仅复刻 `q: str = Query("", min_length=1)`）：
   ```
   omitted q         -> HTTP 422  {'type':'string_too_short','loc':['query','q']}
   q present + empty -> HTTP 422  same
   q present ok      -> HTTP 200
   endpoint actually executed with q = 'x'      ← 422 的两例里端点从未运行
   ```
   → FastAPI（0.135.3 / pydantic 2.12.5）**会校验默认值**，`min_length` 使省略 `q` 直接 422。

2. **真实改造前代码实验**：用 `before/` 的原始 `app/main.py`，在进程内载入真实 `.env`
   （凭据不落屏幕）使 DB 可达 —— 否则依赖注入会先抛 500，测不到校验层：
   ```
   credentials loaded: [DB_HOST, DB_NAME, DB_PASSWORD, DB_PORT, DB_USER, TS_ENDPOINT]
   NO q at all  -> HTTP 422  VALIDATION: string_too_short
   q=''         -> HTTP 422  VALIDATION: string_too_short
   q='%'        -> HTTP 200  total=5571     ← 只有显式通配符才会「返回全部」
   q='0'        -> HTTP 200  total=5152
   ```
   → 与后端 agent 的报告一致。`q='%'` 能取到全部是 **LIKE 的正常语义**，不是校验缺口。

**我犯错的机制**（值得记录，因为这是第二次同类错误）：我看到 OpenAPI 把 `q` 描述成
「可选、默认 `''`」，就把**schema 的描述**当成了**运行时的行为**，
没有执行一次就下了「数据暴露」级别的结论。**这与我在 6.2.1 XSS 上的失误同源：
用静态阅读代替一次运行。**

**剩下的真缺陷**（已收窄，级别 P1 → **Low**）：`Query("", min_length=1)` 会让自动生成的
OpenAPI 把一个**事实必填**的参数描述成可选 → 客户端代码生成器会产出错误的调用契约。
**后端已修**（`app/routers/stocks.py:33` 改为 `Query(..., min_length=1)`），
`/openapi.json` 现在正确标注 `q` 为必填。**本条关闭。**
