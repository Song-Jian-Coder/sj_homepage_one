## 3. 发现并修复的真实缺陷：fundflow 窄屏横向溢出

### 现象

`theme-check.js` 在 390px 视口报 `scrollWidth=514 clientWidth=375`。

### 定位

逐元素测量 `getBoundingClientRect().right`：

```
header > .wrap.bar   scrollWidth=514  clientWidth=375   overflowX=visible
  .live              left=266 right=466  w=200  （固定内容宽 + flex:none）
  #themeSw           left=484 right=514  w=30   ← 主题按钮被挤出可视区
```

`.market-strip` 已在 760px 断点隐藏，但 `.live` 仍占 ~200px，叠加品牌 / 控制台按钮 / 主题按钮，
把顶栏撑到 514px。`body{overflow-x:hidden}` 只是**视觉掩盖**，`documentElement.scrollWidth` 仍暴露，
且**主题切换按钮实际点不到**。

### 修复

```css
@media (max-width:560px){
  .bar{gap:10px}
  .live{min-width:0;flex:0 1 auto;overflow:hidden;padding:0 8px}
  .live #liveText{display:none}   /* 状态点保留，文字让位给主题按钮 */
}
```

修复后 390px：`scrollWidth=375 clientWidth=375`，主题按钮回到视口内。

### 对 09 报告的勘误

09 §4.1 的验收表写 fundflow `light-390`「横向溢出 无」。按 `documentElement.scrollWidth`
复测为 514px —— **该结论不成立**，当时应是按 `body.scrollWidth` / 目视口径测量，被
`overflow-x:hidden` 掩盖。本报告以逐元素矩形为准，并把该断言固化进 `theme-check.js`。

## 5. 环境逼出来的设计决定与一次真实事故

这三个都不是“顺手优化”，是实测失败后改的，记录下来避免以后重犯：

1. **后台启动不能用 `Start-Process`**
   在裁剪过 `PATHEXT` 的 shell 里，`Start-Process` 走 shell 关联解析，对合法绝对路径也报
   「系统找不到指定的文件」。改用 `ProcessStartInfo`（仍失败）→ 最终用 `scripts/serve.py`
   以 `subprocess + DETACHED_PROCESS` 启动，stdio 直接指向日志文件。

2. **不能让子进程继承调用方的 stdout**
   uvicorn 继承 PowerShell 的 stdout 管道后，调用方（本仓库的校验包装、CI）读管道会一直等到
   uvicorn 退出才拿到 EOF —— 表现为「启动命令挂死」。`serve.py` 把 stdio 重定向到文件，
   自己立即退出并回打 PID。

3. **PS 5.1 不能用 `add_OutputDataReceived` 做日志重定向**
   事件回调在无 runspace 的线程执行，抛 `PSInvalidOperationException`，进程直接崩。
   最终方案见上：日志由子进程自己写文件。

另外两个路径坑（仓库路径含 `[AI工作区]`）：

- `Split-Path -Parent $PSScriptRoot` 会把 `[AI工作区]` 当通配符 → 返回 `$null`；
  且 PS 5.1 的 `Split-Path -LiteralPath` **不支持** `-Parent`。统一改 `[System.IO.Path]::GetDirectoryName()`。
- `$env:LOCALAPPDATA` 在受限环境可能为空，直接 `Join-Path` 会抛参数绑定异常；
  `lib-python.ps1` 改为逐项判空 + .NET `GetFolderPath` + 扫描用户目录兜底。

## 5.1 事故复盘：README 的复制命令覆盖了 `.env`

**这条是本报告交付后真实发生的，比前面三条“环境限制”严重得多，单独记。**

### 现象

用户按 README 执行启动，uvicorn 报 `[Errno 10048] error while attempting to bind on
('127.0.0.1', 8000)`；释放端口后服务起来了，但 `/api/v1/health` 返回 `db=down`。

### 根因

`backend/api_run.log`：

```
pymysql.err.OperationalError: (1045, "Access denied for user 'root'@'localhost' (using password: NO)")
API_START config={... "token_len": 0, "db_password_set": false ...}
```

即 **`.env` 没被读到**。核对发现 `backend\.env` 与 `.env.example` 的 SHA256 **完全相同**：

```
backend\.env   A8AAFBF3...627A7193
.env.example   A8AAFBF3...627A7193
```

而 README 第 2 步写的是：

```powershell
Copy-Item .env.example backend\.env      # ← 无条件覆盖
```

`Copy-Item` **保留源文件的 LastWriteTime**，所以 `.env` 的 mtime 仍是 10/6，从时间戳完全看不出被覆盖。
后果：`DB_PASSWORD`、`ADMIN_KEY`、`TS_TOKEN_FILE` 全部被冲成模板值（空 / 占位符）。

### 修复

1. **README**：复制改为存在性判断，并加警告。

   ```powershell
   if (-not (Test-Path backend\.env)) { Copy-Item .env.example backend\.env }
   ```

2. **`start.ps1`**：原实现只要进程活着就打印 `Healthy (db=down)` 并 **exit 0** ——
   与 `/api/v1/health` 的设计（DB 不可达仍返回 HTTP 200）叠加，正好把故障伪装成成功。
   现在 `db≠up` 时打印 `api_run.log` 尾部、给出 1045/2003 的判别提示、**exit 1**。
3. **`stop.ps1`**：补一条兜底 —— uvicorn 在 Windows 上会 spawn 子进程（日志
   `Started server process [<pid>]`），实际监听端口的是子进程；父进程正常退出会带走子进程，
   但父进程崩溃会留下占端口孤儿，因此停完父进程后再检查端口，仍被本项目 uvicorn 占用就一并停。
4. **`backend\.env`**：已恢复 `TS_TOKEN_FILE=C:\Users\57424\jsdata_tk.csv`（路径，非凭据，
   恢复后 `token_len` 从 0 变回 56）。`DB_PASSWORD` / `ADMIN_KEY` **不猜、不写**，由使用者填回。

### 教训

- 文档里的“复制模板”命令是**破坏性操作**，必须带存在性判断；`Copy-Item` 保留 mtime 会让事故隐形。
- 健康检查的“进程在” ≠ “服务可用”。凡是有独立 `db` 状态位的接口，脚本必须按 `db` 判定成败。
- §4 的验证记录（26/26、pytest 59 passed）是在 `.env` 完好时取得的；`.env` 被覆盖后 DB 不可达，
  属于配置故障而非代码回归，重新填好 `DB_PASSWORD` 即可复现原结果。

### 5.2 现象：改了前端，浏览器仍显示旧页面（「模拟数据」+ 配色不变）

**另一类“看起来没生效”，根因不在代码。**

### 现象

使用者打开 `http://127.0.0.1:8000/fundflow.html`：

- 顶栏状态显示 **「模拟数据」**（数据不是真的）；
- `admin.html` / `industry.html` 的配色「仍未有变化」（不是明亮主题）。

### 取证（先证明服务端是对的）

用无头 Edge（`Network.setCacheDisabled`）加载三页：

| 页面 | data-theme | body bg | 关键内容 |
|---|---|---|---|
| fundflow | light | `rgb(251,252,253)` | `liveText="真实数据 · 数据日期 2026-10-19"`，134 个 `.tile` |
| industry | light | `rgb(251,252,253)` | `31 一级 · 134 二级 · 346 三级 · 4938 只` |
| admin | light | `rgb(251,252,253)` | 无异常 |

三页 `exceptions: none`，`SW` 导出 28 个成员（含 `themeGet`）。服务端响应 200 / 41043 B / 正确 ETag。

结合源码可确认「模拟数据」只可能是**未被覆盖的静态占位**：`fundflow.html` 的 `init()` 只有两个终态
（成功写「真实数据 · 数据日期 …」，失败写「数据加载失败」），停在占位说明脚本根本没执行到那里 ——
典型原因是浏览器用了旧版 `common.js`（没有 `themeGet`，`tileColor()` 一调用就抛错）与旧版 HTML。

### 根因

`StaticFiles` 只发 `ETag` + `Last-Modified`，**没有 `Cache-Control`**。浏览器对这种响应走启发式缓存，
在“文件已更新但缓存未过期”的窗口里直接复用旧副本，既不发请求也不提示。

### 修复

`app/main.py` 新增 `cache_policy` 中间件，对 `text/html`、`text/javascript`、`application/javascript`、
`text/css` 统一补 `Cache-Control: no-cache`（可缓存，但每次使用前必须校验）：

```python
resp = await call_next(request)
ct = resp.headers.get("content-type", "")
if ct.startswith(("text/html", "text/javascript", "application/javascript", "text/css")):
    resp.headers["Cache-Control"] = "no-cache"
return resp
```

`no-cache` 而不是 `no-store`：配合 ETag，文件没变时是 304，几乎零开销；
不能只靠“让用户按 Ctrl+F5”，那是把工程问题转嫁给使用者。

### 验证

```
/fundflow.html  200  41043 B  Cache-Control=no-cache  ETag="2fd1d254..."
/industry.html  200 120121 B  Cache-Control=no-cache  ETag="f40c8d63..."
/admin.html     200  38279 B  Cache-Control=no-cache  ETag="fcc52717..."
/common.js      200  12990 B  Cache-Control=no-cache  ETag="00f69ef7..."
If-None-Match: <etag>  ->  304
/api/v1/health  200  Cache-Control=（不设置，JSON 不参与缓存策略）
```

`scripts\check.ps1` → **26/26**（theme 60/60、regress 24/24、pytest 59 passed）。

### 教训

- 单文件前端（无构建、无 hash 文件名）必须显式声明 HTML/JS/CSS 的缓存策略，
  否则“改了没生效”会反复发生，而且表现得像功能 bug（假数据、主题不切换）。
- 排查顺序应该是：**先证明服务端产物是对的**（禁用缓存的真实浏览器 + HTTP 头），再怀疑代码。
  本次若先读代码，会在 `init()` 里绕很久。
